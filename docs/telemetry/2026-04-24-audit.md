### A2.2 The single backend Sentry path: SQL pg_net dispatch

The ONLY backend Sentry capture path is pg_net HTTP POSTs from two
SECURITY DEFINER plpgsql functions. Source: migrations
`20260424000001_cost_anomaly_sentry_dispatch.sql` (retired phase-1
unconditional-stamp version) and
`20260424000004_cost_anomaly_two_phase_dispatch.sql` (current
two-phase version).

**Phase 1 — `stir_ops_cost_anomaly_alert_dispatch()`** (enqueue):
- Reads DSN from `app_settings WHERE key='SENTRY_DSN'` (`:83`).
- Parses DSN via regex into `public_key`, `host`, `project_id`.
- Builds Sentry store-endpoint URL: `https://<host>/api/<project_id>/store/?sentry_key=<public_key>&sentry_version=7`.
- For each unsent row (up to 50/tick), POSTs a Sentry event body and
  captures pg_net's `request_id` into `cost_anomalies.sentry_request_id`.
- Batch-stamps `dispatched_at = now()` after all pg_net calls fire
  (W15 — single UPDATE via UNNEST, `20260424000004:147–151`).

**Phase 2 — `stir_ops_cost_anomaly_alert_confirm()`** (verify):
- Reads `net._http_response` for rows with `dispatched_at IS NOT NULL
  AND confirmed_at IS NULL`.
- 2xx → stamps `confirmed_at = now()`.
- 4xx/5xx or timeout before 5 retries → clears `dispatched_at` +
  `sentry_request_id` + bumps `confirm_attempts` so phase 1 re-picks.
- 5-retry cap → stamps `confirmed_at` + RAISE WARNING + stop.

Both functions run via `pg_cron` every 1 minute.

### A2.4 Migration order note

Both `20260424000001` and `20260424000004` exist. `000001` is the
supersedes-target (single-phase, unconditional-stamp, the
fire-and-forget reliability hole). `000004`'s backfill handles rows
stamped before `000004` landed. **(fact — migration 000004 docstring
lines 43–49)**. Phase D should tag `000004`; `000001` is dead code but
still in the file list (regexp parse in 000001 has weaker log
redaction; do not refactor per "don't add capture where none exists"

truncates to `length + prefix(20)` per W25. If `000001` ever runs, it
leaks the public key. **(fact — observed in source)**

## A4 — Property consistency

### A4.1 User-identity property naming (canonical SHA-256 prefix)

The SAME 16-char SHA-256 hash of `canonical_user_key` is referenced
under **five different property / field names** across surfaces:

| Name | Location | Kind |
|---|---|---|
| `canonical_user_key_hash` | Backend PostHog (distinct_id, not a property name) · iOS PostHog `app_opened.canonical_user_key_hash`, `onboarding_started.canonical_user_key_hash` | identifier |
| `canonical_key_hash` | iOS Sentry context (every captureError + breadcrumb in RootCoordinator + SupabaseSessionClient) | Sentry tag |
| `user_hash` | Backend SQL Sentry event `tags.user_hash` (from `cost_anomalies.canonical_user_key_hash`) | Sentry tag |
| `keyHash` (Swift var) / `user.userId` (Sentry SDK) | `SentryReporter.setUserContext` | Sentry user binding |
| `canonical_user_key_hash` | Backend `cost_anomalies` table column + `ops_flagged_outputs` table column | DB column |

All resolve to the same hex string. **A dashboard joining Sentry to
PostHog cannot use a single property name — cross-surface SQL/analytics
would need string mapping.** Phase B schema must pin one canonical name
and deprecate the others.

### A4.2 `request_id` / correlation-key proliferation

The backend carries `request_id` universally (every `/v1/*` handler
gets one via `requestIdFrom(req)` at `_shared/logger.ts:80–84`;
echoed on `x-request-id` response header). It IS the canonical
cross-system join key.

But backend-internal correlation-ids are NOT uniformly exposed to
PostHog. Each feature uses its own id as `$ai_trace_id`:

| Feature | `$ai_trace_id` value | PostHog property name | Conflict with `request_id`? |
|---|---|---|---|
| dinner-solve | `body.solve_request_id` | `$ai_trace_id` | distinct |
| cook-turn | `body.client_request_id` | `$ai_trace_id` | distinct |
| pantry-parse | `body.client_request_id` | `$ai_trace_id` | distinct |
| substitution | `body.sub_event_id` | `$ai_trace_id` | distinct |
| recipe-import | `body.import_id` | `$ai_trace_id` | distinct |
| grocery-generate | `body.source_id` | `$ai_trace_id` | distinct |
| voice-cook-turn | `body.session_id` | `$ai_trace_id` | distinct |
| pgmq-dispatch (async recipe) | `payload.import_id` | `$ai_trace_id` | distinct |

`$ai_span_id = rowEntry.request_id` is always the iOS-supplied
feature-specific id (`solve_request_id`, `client_request_id`, etc.),
**NOT the Edge Function's `x-request-id` header**. So on the PostHog
side, there's a reliable surrogate for "which iOS-originated call
produced this AI generation" — but no direct join from a PostHog
event to a Supabase Edge Function log line, because the function log's
`request_id` and the event's `$ai_span_id` are different values.

iOS-side event properties: `session_id` (voice), `sub_event_id`
(substitution), `source_id` (grocery), `import_id` (import),
`solve_request_id` (solve), `client_request_id` (cook-turn fallback +
pantry-parse). Same drift as backend. **(inference)**

| Backend function log entries (stdout JSON) | ✅ always | `_shared/logger.ts:44–50` stamps on every entry | `logger.ts` is the mandatory wrapper — every handler creates a logger with `requestId` |
| Backend PostHog `$ai_generation` | ⚠️ surrogate | `$ai_span_id = ai_request_log.request_id = iOS-body id` | NOT the Edge Function's x-request-id header. Feature-specific id (`solve_request_id` etc.) — usable for iOS↔PostHog join, not PostHog↔Supabase-log join |
| Backend SQL Sentry dispatch (cost_anomaly) | ❌ | tags carry `anomaly_type`, `severity`, `user_hash` only | anomaly row `id` is an `event_id` but no request_id concept |
| iOS PostHog — AI events (`ai_request_failed`, `cook_turn_resolved`) | partial | `cook_turn_resolved` has no id at all on Live path (VAD-driven); fallback includes `client_request_id` via the surrounding flow (not explicitly in the event) | |
| iOS PostHog — non-AI events | ❌ | `app_opened`, `scan_submitted`, `constraints_set`, etc. — none carry `request_id` | |
| iOS Sentry `captureError` | ❌ | 3 sites, zero include `request_id` | `SupabaseSessionClient` has the `x-request-id` in the HTTP response but doesn't thread it to `sentry.captureError` |
| iOS Sentry `breadcrumb` | ❌ | 4 sites, zero include `request_id` | same gap |

**Net cross-system join posture:**

- iOS PostHog product event ↔ backend PostHog `$ai_generation` — joinable
  on the feature-specific id (`solve_request_id` etc.) via
  `$ai_span_id`. **(inference — works for AI features where both
  sides emit the same id; no join for non-AI events.)**
- Any PostHog event ↔ backend function log — joinable only when the
  backend honored an iOS-sent `x-request-id` header (if iOS sends
  one; I did NOT verify iOS outbound; `requestIdFrom` at logger.ts
  accepts an incoming header but I haven't confirmed iOS sets it on
  every `/v1/*` call).
- iOS Sentry event ↔ backend Sentry event — **NOT joinable on
  `request_id`** (neither side carries it).
- iOS Sentry event ↔ iOS PostHog event of the same causal chain — NOT
  joinable on `request_id` (Sentry doesn't get request_id tagged).
- Backend Sentry event (cost_anomaly) ↔ backend PostHog event (`$ai_generation`)
  — joinable on `user_hash`/`distinct_id`, but only at the USER level,
  not the REQUEST level.

**The dashboard-readiness question "can I trace a user complaint from
an iOS Sentry error back to the exact backend function call and its
$ai_generation event?" is NO today.** The missing links are:
- iOS Sentry needs to tag `request_id` from the HTTP response
- Backend SQL cost-anomaly dispatch needs to tag `request_id` (or its
  substitute, the `anomaly_id` carrying a detection-run id — but
  request_id is more broadly useful)
- Backend function log ↔ PostHog event needs a consistent id; today
  the function log uses `requestIdFrom` and PostHog uses the iOS-body
  id; dashboard-join requires standardizing to one.

### G10 — `request_id` surrogate vs real on PostHog side

**(fact — A5)** `$ai_span_id` stores the iOS-supplied feature id, not

- property-name typos ship silently (one reason the `TelemetryEvent`

- retrofit to the Phase B canonical schema requires either builders

Not blocking; good to note for Phase B design.
